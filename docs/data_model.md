# Модель данных и правила варианта 3

Схема и БД — `sergey_rodionov`. Модели: [app/models.py](../app/models.py).
`init-db` создаёт схему и таблицы; повторный запуск безопасен, но не выполняет миграции.

| Таблица | Поля |
|---|---|
| users | id bigint PK; login varchar(64); password_hash text; full_name varchar(200) |
| specialists | id bigint PK; full_name, specialization varchar(200) |
| services | id bigint PK; name varchar(200); duration_minutes integer > 0 |
| slots | id bigint PK; specialist_id FK; service_id FK; starts_at, ends_at timestamptz; ends_at > starts_at |
| appointments | id bigint PK; slot_id FK; created_by_id FK; client_name, client_contact varchar(200); status varchar(16); created_at timestamptz; cancelled_at timestamptz, допускается null |

Все поля, кроме `cancelled_at`, обязательны. Связи 1:N: специалист → слоты,
услуга → слоты, слот → записи (включая историю отмен), оператор → записи.
CHECK ограничивает status значениями booked/cancelled и связывает его с cancelled_at.
На момент измерений — пять PK-индексов по [сохранённой проверке](../measurements/verification.json); дополнительных индексов нет. Внешние ключи заданы в моделях, отдельных индексов для них нет.

## Бизнес-правила

- Слот предназначен для одной услуги и бронируется целиком; длительность должна совпадать с услугой.
- Интервалы полуоткрытые: соседние приёмы разрешены, наложение на действующую запись запрещено.
- Seed создаёт непересекающиеся слоты специалиста. Ручного изменения расписания нет.
- Создание блокирует выбранный слот SELECT FOR UPDATE и проверяет занятость в той же транзакции.
  Это защищает один слот; произвольное расписание с пересекающимися слотами здесь не реализовано.
- Отмена сохраняет запись и освобождает слот. Повторная отмена не меняет cancelled_at.
- Загрузка = минуты действующих записей / минуты расписания × 100; без расписания — null.
  Обе группы интервалов обрезаются границами периода и отдельно объединяются без двойного учёта.
- Доля отмен = отменённые / все записи (booked и cancelled), пересекающие период, × 100; без записей — 0.
  Отбор ведётся по интервалу приёма, независимо от created_at и cancelled_at. Проценты округляются до двух знаков.
- Для сводки период — [00:00 date_from, 00:00 дня после date_to) в Europe/Moscow.
  Входят интервалы с starts_at < верхняя граница и ends_at > нижняя граница.
- Даты периода включают оба календарных дня по Москве. Список и поиск слотов отбираются по началу приёма.
  Время хранится с часовым поясом, интерфейс показывает МСК. Историческое бронирование разрешено.

Одна роль — оператор, все записи ему доступны. Сессия — подписанная cookie
(HttpOnly, SameSite=Lax, 8 часов), пароль — PBKDF2-HMAC-SHA256, 210000 итераций.
Фиксированная соль применяется только к воспроизводимому оператору seed.

## Проверка выбранных SQL-операций

Проверка исходников 08.10.2026, без запуска тестов и HTTP-сценариев.
Сопоставлены [api.py](../app/api.py), [schemas.py](../app/schemas.py),
[services.py](../app/services.py), [auth.py](../app/auth.py) и существующие
[тесты контракта](../tests/test_api.py); их успешный прогон сохранён в
[dz1_pytest.txt](dz1_pytest.txt), функциональная проверка — в [dz1_clean_start.txt](dz1_clean_start.txt).

| Операция | Назначение запросов при измеренных параметрах | Число по диагностике |
|---|---|---:|
| Свободные слоты | Пользователь; существование услуги; COUNT свободных слотов; отсортированная страница | 4 |
| Список записей | Пользователь; COUNT отфильтрованных записей; отсортированная страница | 3 |
| Создание | Пользователь; блокировка слота; услуга; проверка пересечения; INSERT; полная карточка | 6 |
| Сводка | Пользователь; интервалы расписания; записи с интервалами слотов; список специалистов | 4 |

COUNT и страница используют одинаковые фильтры, но имеют разное назначение.
ORDER BY, OFFSET и LIMIT ограничивают страницу; сериализаторы используют уже соединённые
таблицы. В моделях нет ORM relationships с ленивой загрузкой. В циклах обработки
строк выбранных функций SQL не вызывается; db.execute/db.scalars в заголовке for
выполняется один раз, затем перебирается результат. Коррелированный EXISTS — часть
SQL-запроса, а не отдельный HTTP/SQL-вызов для каждой строки.

В просмотренных API-функциях не найден очевидный повтор одного запроса с одинаковым
назначением. Тесты проверяют поля карточки, фильтры, разные страницы, пустую страницу
за концом списка, 401/404/409/422 и формулы сводки. Это ограниченная проверка выбранных
операций и параметров: полный трассировочный журнал SQL и все возможные сценарии не исследованы.
