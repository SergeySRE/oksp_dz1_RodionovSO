## 1 Сервис, стенд и данные

### 1.1 Сценарии и структура данных

Авторизация — подписанная cookie-сессия, HttpOnly, SameSite=Lax.
Демонстрационный оператор — demo. Пароль хранится как PBKDF2-SHA256 хеш.
Выход очищает сессию; API без авторизации возвращает 401, HTML перенаправляет на /login.

Реализованы:

- список /appointments с фильтрами по статусу, услуге, специалисту и датам, постраничный вывод;
- карточка /appointments/{id} со слотом, специалистом, услугой и оператором;
- поиск и создание через /booking;
- отмена кнопкой в карточке, сохранение cancelled_at и возможность повторного бронирования;
- /summary с периодом, загрузкой специалистов и долей отмен;
- вход /login и выход из панели навигации.

Обязательные экраны методички: список с фильтром/пагинацией, карточка со связями и сводка.
Сводка не ограничивается текущей страницей: обрабатывает все данные выбранного периода.

| Таблица | Поля | Связи |
| --- | --- | --- |
| users | id bigint PK; login varchar(64); password_hash text; full_name varchar(200) | Оператор записи |
| specialists | id bigint PK; full_name varchar(200); specialization varchar(200) | 1:N slots |
| services | id bigint PK; name varchar(200); duration_minutes integer > 0 | 1:N slots |
| slots | id bigint PK; specialist_id FK; service_id FK; starts_at, ends_at timestamptz; ends_at > starts_at | N:1 specialist/service; 1:N appointments (история) |
| appointments | id bigint PK; slot_id FK; created_by_id FK; client_name, client_contact varchar(200); status varchar(16); created_at timestamptz; cancelled_at nullable timestamptz | N:1 slot/user; status booked или cancelled |

Поля обязательны, кроме cancelled_at. CHECK связывает статус и наличие даты отмены.
Сохраняются пять PK-индексов; дополнительных индексов нет. Активные записи одного
специалиста проверяются на пересечение полуоткрытых интервалов [начало, конец).
Отмена повторно не меняет первоначальное время отмены. Загрузка — занятые минуты /
минуты расписания × 100; перекрывающиеся интервалы учитываются один раз.
Доля отмен — отменённые / все записи, пересекающие выбранный период × 100.
При пустом расписании загрузка null («Нет расписания»), при отсутствии записей доля отмен 0.

Код организован просто: app/api.py и app/pages.py вызывают общие функции app/services.py;
app/models.py содержит ORM-модели; app/auth.py — авторизацию; app/seed.py — наполнение;
app/measurement.py — измеритель; app/observation.py — SQL-наблюдение;
templates/static — клиентские страницы; tests — проверки.


Тело POST — JSON с Content-Type: application/json.
После входа клиент передаёт полученную cookie; браузер делает это автоматически.
Все операции, кроме входа, требуют авторизации.

| Метод и путь | Параметры / тело | Успешный ответ | Ошибки |
|---|---|---|---|
| POST /api/auth/login | login, password | 200: id, login, full_name; Set-Cookie | 401, 422 |
| POST /api/auth/logout | нет | 204 без тела; удаление cookie | 401 |
| GET /api/services | нет | 200: массив id, name, duration_minutes | 401 |
| GET /api/specialists | service_id > 0, необязательный | 200: массив id, full_name, specialization; услуга без специалистов даёт [] | 401, 422 |
| GET /api/slots | service_id, date_from, date_to; specialist_id; page=1, size=20 | 200: items свободных слотов, total, page, size | 401, 404, 422 |
| GET /api/appointments | page=1, size=20; status, specialist_id, service_id, date_from, date_to | 200: items записей, total, page, size | 401, 422 |
| GET /api/appointments/{id} | положительный id | 200: полная запись | 401, 404, 422 |
| POST /api/appointments | slot_id, client_name, client_contact | 201: полная созданная запись | 401, 404, 409, 422 |
| POST /api/appointments/{id}/cancel | положительный id | 200: полная отменённая запись; повторный вызов возвращает то же время отмены | 401, 404, 422 |
| GET /api/summary | date_from, date_to | 200: показатели сводки | 401, 422 |

Параметры дат — YYYY-MM-DD; date_to не раньше date_from.
Идентификаторы положительные, page ≥ 1, 1 ≤ size ≤ 100.
status — booked или cancelled. Длина ФИО и контакта 1–200 символов после удаления пробелов по краям.
Неизвестные поля POST отклоняются с 422.

Полная запись:
`id, status, client_name, client_contact, created_at, cancelled_at,`
`slot: {id, starts_at, ends_at}, specialist: {id, full_name, specialization},`
`service: {id, name, duration_minutes}, created_by: {id, full_name}`.
Список возвращает тот же формат каждой записи.

Свободный слот:
`id, starts_at, ends_at, specialist: {id, full_name}, service: {id, name, duration_minutes}`.

Сводка:
`date_from, date_to, total_appointments, cancelled_appointments, cancellation_percent,`
`specialists: [{specialist_id, full_name, scheduled_minutes, booked_minutes, load_percent}]`.

Даты и время JSON — ISO 8601 с часовым поясом; cancelled_at может быть null.
Список записей сортируется по starts_at DESC, id DESC;
свободные слоты — starts_at ASC, id ASC; справочники и специалисты сводки — id ASC.
total относится ко всему отфильтрованному набору; страница за его концом содержит пустой items.
Отсутствующие объекты при чтении карточки, бронировании и отмене дают 404.
Несуществующие идентификаторы в фильтрах списка дают пустой результат.
В поиске слотов отсутствующая услуга или специалист дают 404.
409 означает занятый слот, пересечение с записью или несоответствие длительности.

Ошибка предметной операции имеет вид `{"detail": "сообщение"}`.
Ошибка валидации FastAPI — `{"detail": [{loc, msg, type, ...}]}`.
При некорректных параметрах и отсутствии входа порядок проверки не считается гарантией:
корректный неавторизованный запрос получает 401, некорректный может получить 422.
Автоматическая схема: /openapi.json; интерактивная документация: /docs.

HTML-страницы — клиентский интерфейс, отдельный дублирующий контракт для них не ведётся.
Jinja2 вызывает общую бизнес-логику, минимальный JavaScript отправляет изменения в JSON API.

## 2 Измерения

### 2.1 Полное время HTTP-операций

Измерялись все десять операций JSON API реальными HTTP-запросами к работающему
Uvicorn. HTTPX 0.28.1 в обычном режиме stream=False полностью читает ответ
перед возвратом client.request. Таймер охватывает этот вызов. Подготовка cookie,
вход перед выходом, восстановление активной записи, удаление временного создания,
seed и запись файлов находятся вне измеряемого интервала.
Прогрев выполняется тем же способом, но его повторы не сохраняются в выборке.

p50/p95 — линейная интерполяция позиции (n−1)×p в отсортированной выборке;
для n=30 медиана усредняет 15-е и 16-е значения, p95 имеет позицию 27,55 при
нумерации с нуля. Maximum — наибольшее измеренное время.
Каждая строка основана на 30 повторах; все времена ниже в мс.

Рост основной операционной таблицы — 333,33×, слотов — 400×,
специалистов — 20×, услуг — 3×. Ни одна выбранная операция не показала рост p50
выше роста основной таблицы; делать вывод о сверхлинейной сложности по этим
двум точкам нельзя. При этом сводка выросла в 173,54×, свободные слоты — в 36,66×,
список — в 17,72×, создание — в 2,33×, что делает их практически значимыми
кандидатами для исследования.

Правило отбора в инструменте: рост p50 ≥ 2× **и** прирост p50 ≥ 5 мс.
Оно задано до сравнения; это описательное правило, а не статистический тест.
Из дальнейшего разложения исключены login, logout, services, specialists,
appointment_detail и appointment_cancel: в этой серии они не удовлетворили
критерию. Это не доказывает их независимость от объёма при любых нагрузках.
В частности, справочник специалистов вырос с 10 до 200 строк, но его p50 вырос
только с 5,81 до 7,90 мс.

### 2.2 Диагностические средние

SQLAlchemy events before_cursor_execute / after_cursor_execute / handle_error
считают SQL-вызовы и суммарное время cursor.execute; ContextVar ограничивает
накопление текущим запросом, X-Measurement-Id связывает ответ с измерением.
Обработчики не меняют запросы и параметры. В обычных baseline-запросах
диагностические заголовки и накопление метрик отключены.
Все измеряемые ответы — обычный JSON; потоковых ответов и SQL-фоновых задач нет.

Каждый сырой диагностический повтор хранит полное HTTP-время, SQL-время,
число запросов и **остаток = HTTP − SQL этого же повтора**. В таблице — средние
арифметические одной и той же выборки из 30 повторов. SQL-среднее из HTTP-медианы
не вычитается. p50/p95/max диагностических серий доступны в исходных JSON/CSV,
но не подменяют baseline-результаты.

| Операция | Набор | Полное HTTP, среднее мс | SQL, среднее мс | SQL-запросов, среднее (min–max) | Остаток, среднее мс |
| --- | --- | --- | --- | --- | --- |
| Свободные слоты | SMALL | 16,62 | 4,57 | 4 (4–4) | 12,05 |
| Список записей | SMALL | 14,06 | 4,09 | 3 (3–3) | 9,97 |
| Создание записи | SMALL | 20,88 | 5,62 | 6 (6–6) | 15,26 |
| Сводка | SMALL | 15,81 | 3,61 | 4 (4–4) | 12,20 |
| Свободные слоты | WORKING | 409,85 | 398,31 | 4 (4–4) | 11,54 |
| Список записей | WORKING | 208,27 | 197,71 | 3 (3–3) | 10,56 |
| Создание записи | WORKING | 37,72 | 23,06 | 6 (6–6) | 14,66 |
| Сводка | WORKING | 2371,65 | 316,33 | 4 (4–4) | 2055,33 |

На WORKING свободные слоты проводят около 97,18% среднего HTTP-времени в
измеренном cursor.execute; список — около 94,93%; создание — около 61,13%.
Сводка имеет остаток около 86,66% полного среднего времени.
Количество запросов одинаково на SMALL и WORKING: 4/3/6/4 соответственно.
Из этих чисел не следует обращение к БД в цикле: в выбранных функциях набор
запросов фиксирован, а рост происходит при том же их числе.

**Граница наблюдения:** SQL-время включает driver/network во время execute,
но не является чистым серверным временем PostgreSQL. Оно не включает отдельные
commit/rollback, ORM-преобразование и последующую обработку/извлечение результатов.
Остаток включает эти действия, сериализацию, ожидания и HTTP-обмен.
В таблице шаблона «В коде» следует подписать как «Остаток HTTP − cursor.execute»,
а не как чистое время Python.

> Снимок отсутствует; инструкция S05.

## 3 Гипотезы об узких местах

### Гипотеза 1 — поиск свободных слотов

**Установленный факт.** p50 вырос с 10,87 до 398,44 мс (36,66×).
В диагностике WORKING полное среднее 409,85 мс, SQL 398,31 мс, четыре запроса.
Функция free_slots в [app/services.py](../app/services.py) формирует проверку
пересечения через коррелированный EXISTS с appointments и вторым представлением
slots; этот отбор используется и в COUNT, и в запросе страницы с сортировкой.

**Предполагаемая причина.** Проверка пересечений и обработка большого набора
кандидатов в обоих SQL-запросах становятся дорогими при 200000 слотах и 100000
записях. Дополнительных индексов по условиям отбора нет. Это объяснимый кандидат,
но конкретный план выполнения, число просмотренных строк и вклад каждого из
четырёх запросов не измерены. Утверждать конкретный вид сканирования нельзя.

### Гипотеза 2 — список записей

**Установленный факт.** p50 вырос с 11,41 до 202,21 мс (17,72×).
Диагностическое среднее WORKING 208,27 мс, SQL 197,71 мс, три запроса.
appointment_list использует JOIN записи со слотом, специалистом, услугой и
оператором; отдельно вычисляет COUNT результата и получает 20 строк после
ORDER BY starts_at DESC, appointment.id DESC.

**Предполагаемая причина.** Подсчёт всего набора и сортировка связанных записей
обрабатывают существенно больше данных, чем возвращаемые 20 строк.
Рост SQL-времени при неизменных трёх запросах поддерживает гипотезу о стоимости
самих запросов, а не об увеличении их числа. Какой запрос преобладает — COUNT
или получение страницы — суммарный таймер не устанавливает.

### Гипотеза 3 — сводка

**Установленный факт.** p50 вырос с 13,89 до 2409,66 мс (173,54×).
Диагностическое среднее WORKING 2371,65 мс, SQL 316,33 мс,
остаток 2055,33 мс, четыре запроса. summary читает все интервалы слотов и записей
периода, формирует списки по специалистам, затем вызывает merged_seconds с
сортировкой и объединением интервалов. Для годового периода seed это 200000 слотов
и 100000 записей, а не одна страница; ответ содержит показатели 200 специалистов.

**Предполагаемая причина.** Материализация, преобразование дат, обход больших
результатов и обработка интервалов существенно увеличивают остаток вне execute.
Числа согласуются с этим кодом, но остаток не равен CPU-времени Python:
в нём также есть работа драйвера/ORM, передача и извлечение результатов, ожидания
и HTTP. Профилирование на данном этапе не выполнялось, поэтому доли этих действий
не установлены.

### Гипотеза 4 — создание записи

**Установленный факт.** p50 вырос с 17,13 до 39,95 мс (2,33×).
Диагностическое среднее WORKING 37,72 мс, SQL 23,06 мс, шесть запросов;
на SMALL SQL-среднее 5,62 мс. create_appointment блокирует выбранный слот по PK,
читает услугу, проверяет конфликты JOIN appointments/slots по специалисту,
статусу и границам интервала, вставляет запись и получает полную карточку.

**Предполагаемая причина.** Проверка отсутствия пересечения по большому набору
записей может давать основную часть роста SQL-времени. Количество запросов не
изменилось, поэтому гипотеза касается их стоимости. Отдельно не измерены проверка
конфликта, вставка и запрос карточки; назначить весь SQL-прирост одной проверке
на основании суммарного таймера нельзя.

### Очевидные ошибки

При текущей проверке исходников измерителя и выбранных запросов ошибок,
требующих исправления и пересъёма сохранённых серий, не обнаружено.
client.request полностью читает ответ до остановки таймера; прогрев исключён;
prepare/cleanup выполняются вне него; SQL-метрики изолированы текущим запросом;
формулы процентилей, коэффициентов и диагностических средних корректны.
Канонический seed обеспечивает свободный слот и активную запись для изменений.

Соответствие контракту проверялось ранее 60 тестами; результаты сохранены как
агрегированный факт проверки. При просмотре исходников не обнаружены очевидные
повторные одинаковые SQL-запросы в выбранных операциях. COUNT и запрос страницы
возвращают разные результаты и не считаются случайным дублированием.
Однако одно число SQL-запросов не доказывает отсутствие любых лишних обращений:
полного SQL-трейса всех вариантов параметров здесь нет.

На этом этапе приложение, индексы, наполнение и исходные JSON/CSV не изменялись.
Повторные измерения и полный pytest не запускались. Подготовлены только просмотрщик
сохранённых файлов, черновик и материалы проверки. Оптимизация относится к
следующим этапам и здесь не выполнена.

## Заключение

Цель содержательной части этапа достигнута: сервис реализован и исходные показатели
получены. **Комплект сдачи ещё не завершён:** нужны иллюстрации, доступный репозиторий
и окончательное оформление по официальному шаблону.

Для этого решены следующие задачи:

1. Реализованы авторизация, три обязательных экрана, поиск, создание и отмена.
2. Описаны пять таблиц и десять операций JSON API.
3. Подготовлены тесты; предыдущий прогон завершился 60 успешными проверками.
4. Созданы воспроизводимые SMALL с 300 и WORKING со 100000 записями.
5. Сняты по 30 измеряемых HTTP-повторов для десяти операций на каждом наборе.
6. Для четырёх операций сняты диагностические серии по 30 повторов на обоих наборах.
7. Сформулированы четыре гипотезы с числовым обоснованием и опорой на код.
8. Проверены очевидные ошибки и сохранность исходных результатов; оформление
   и обязательные материалы сдачи пока требуют завершения.

Главные кандидаты — сводка, свободные слоты, список и создание.
Сводка имеет p50 WORKING 2409,66 мс и диагностический остаток 2055,33 мс;
для свободных слотов SQL-среднее 398,31 мс из полного 409,85 мс,
для списка — 197,71 из 208,27 мс. Эти результаты устанавливают направление
исследования, но ещё не доказывают конкретные причины и эффект оптимизации.

### Ограничения

- Только один последовательный клиент и один сценарий параметров на операцию;
  это не нагрузочное испытание ДЗ2.
- API-время не включает загрузку HTML/CSS/JS, отрисовку и действия человека в браузере.
- Версии Docker Engine/Compose в старых JSON не записаны; текущие версии нельзя
  подставлять как подтверждённые условия прошлых серий.
- Стенд Docker/WSL2; клиент и сервер делят ресурсы машины. Системные ожидания,
  autovacuum и физическое состояние буферов/статистики PostgreSQL отдельно не фиксировались.
- Восстановление между изменениями сохраняет логические строки и последовательность,
  а не идентичное физическое MVCC-состояние. Подготовка может прогревать страницы.
- 30 повторов позволяют получить описательные p50/p95/max; независимые серии,
  доверительные интервалы и статистическая значимость не исследованы.
- Диагностический режим добавляет затраты наблюдения и снят отдельной серией.
  Его средние нельзя смешивать с медианами baseline.
- SQL-сумма не показывает время отдельных запросов и не является чистым временем
  PostgreSQL; остаток не является чистым временем Python.
- Правило выбора четырёх кандидатов практическое; два объёма не определяют
  асимптотическую сложность и не доказывают независимость исключённых операций.
- Запуск с чистого окружения на чужой машине по README в текущей проверке не подтверждён.
- Часть формулировок п. 2.10 недоступна в извлечённом тексте и остаётся непроверенной.
